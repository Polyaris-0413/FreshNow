# 到期提醒：每天一条「即将过期」，一条「已过期」

日期：2026-10-20　状态：**暂缓（未实施）**

## 结论：暂缓

需求本身成立，但 2026-10-20 与用户讨论后决定暂不实现。原因不在功能，而在**这功能对目标用户群的送达率不可靠**：

- 用户群里几乎全是国产 ROM。
- 「从最近任务划掉」在部分国产 ROM 上等同强制停止（厂商行为，见「风险」）。而强制停止之后，包处于 stopped state，收不到任何广播、重启也不恢复，只能等用户手动打开应用。
- 「吃东西前先打开应用看一眼」本身就不符合使用习惯，所以应用内首页兜底**不能**当成等效替代。
- 剩下唯一真正可靠的手段是前台服务常驻通知栏，代价与「不在后台常驻、不挂常驻通知」的红线直接冲突，不值得。

本文件的「技术设计」与「风险」两节在重新提起时仍然有效，不必重查：其中记录了 force-stop 与 stopped state 的边界、应用休眠的影响、以及用户侧需要做的四项设置。

## 为什么

东西放进冰箱之后，只有用户自己记得它还在。过期这个事实，应用早就知道（`ExpiryCalculator` 天天在算），却从来没主动说过一次——用户要打开应用、翻列表、看日期，才知道有东西快坏了。

应用没有接推送，也不需要接。推送（FCM / 厂商通道）解决的是「服务端在没有运行的应用上叫醒它」；这件事里根本不存在服务端：过期日期在本地数据库里，日期到了就是到了。所以走**本地通知 + 系统定时任务**，离线、不依赖任何第三方、不要服务器。

## 目标

- G1 每天早上发一条「即将过期」，列出还剩 ≤3 天的东西与各自剩余天数。
- G2 每天早上发一条「已过期」，列出已经过期的东西与各自过期天数。
- G3 同一样东西过期后只提醒一次，之后不再提。
- G4 点通知进首页。
- G5 同一天最多各发一次：排查任务多跑了几遍，用户也只看到一条。

## 非目标

- N1 不接推送，不引入任何服务端。
- N2 不做应用内设置项：阈值固定 3 天、时刻固定上午 8:00，不给用户调（用户已定）。
- N3 不做精确闹钟（`setExactAndAllowWhileIdle` 及其权限、厂商审核一概不碰）。晚一两个小时对这个场景没有影响。
- N4 不做通知内操作：通知里只有「查看」一下，处理东西仍然进应用。
- N5 不做逐条记录一条通知、不做分组子通知（讨论过，A 方案的「拆两条」已定）。
- N6 不给通知文字着色、不用 RemoteViews 自定义布局。纯文本通知的正文只允许一种颜色，为一行字的颜色去自绘布局不值。

## 反目标

- A1 同一天内，同一条通知出现两次。
- A2 已经提醒过的过期项第二天又冒出来。
- A3 通知里出现已经不存在的记录（已删除 / 已从别的设备同步掉）。
- A4 应用因为这件事在后台常驻、或挂一条不可移除的通知。
- A5 通知文案另起一套说法，与列表里的「还剩 N 天 / 今天到期 / 已过期 N 天」不一致。

## 约束

- 过期日期只有 `ExpiryCalculator.resolve()` 一个来源，剩余天数只有 `daysRemaining()` 一个算法。本功能不新增任何日期解析，也不缓存算出来的日期（记录改了要能立刻反映）。
- 文案只用 `res/values/strings.xml` 里已有的保质期说法；新增串也只围绕它们拼。
- 颜色只从 `ui/theme/Color.kt` 取：即将过期用 `Warning40`，已过期用 `Error40`（通知的强调色，即小图标与系统强调色，不是文字色）。
- `minSdk 26`、`targetSdk 37`，纯 Kotlin + AndroidX，不引入第三方库；新增依赖仅 `androidx.work:work-runtime-ktx`。
- 新增通知渠道一旦发布就改不了重要性，首次取值必须想清楚（见 J4）。
- 本功能不动界面，**baseline profile 不需要重录**。

## 我定的（实施时可推翻，但要说明理由）

| 编号 | 决定 | 理由 |
|---|---|---|
| J1 | 每天 **08:00 起的一小时内**触发（`setWindow` 的 1 小时窗口），不是准点 08:00 | 早饭与备餐之间，用户还能安排当天吃掉；再晚就变成「今天已经来不及了」。窗口是 N3 的必然结果——不承诺准点，只说「早上」 |
| J2 | 触发用**两条独立通道**：AlarmManager 的非精确闹钟（主）+ WorkManager 每日周期任务（兜底），外加开机重排与应用启动补查 | 小米、OPPO、vivo 这类系统对 JobScheduler 与 AlarmManager 的拦截策略不同，一边被打掉另一边还可能活。任何单通道方案在这些机型上都不保证 |
| J3 | 「已提醒」不进 `scan_records` 表，用 DataStore 存一个 `syncId#过期日期` 的集合 | 它是**本机行为**，不是记录的内容：进了表就要参与同步与 LWW，两台设备会互相把对方的提醒状态盖掉，反而更乱。用 `syncId#日期` 而不是单纯的 `syncId`，是为了让「用户把过期日期改到更晚」之后那条还能再提醒一次 |
| J4 | 通知渠道建两个：`expiry_soon`（即将过期）与 `expiry_expired`（已过期），重要性都用 `IMPORTANCE_DEFAULT` | 分两个渠道，用户可以在系统设置里只关掉其中一类。不用 HIGH：每天固定响会形成骚扰，横幅留给真正紧急的事 |
| J5 | 通知 ID 固定（2001 / 2002） | 同一类提醒重复发布时原地替换，不堆叠（A1 的第二道保险） |
| J6 | 正文最多列 **5 行**，超出时最后一行写「另有 N 件」 | 通知展开高度有限；5 行之后的名单在应用里看更合适 |
| J7 | 当天到期的算「即将过期」，文案用现有的「今天到期」 | 还没过期就还是「该吃掉」，不是「别吃了」 |
| J8 | 过期日期认不出来的记录（推算失败）不参与提醒 | 不知道哪天到期，就没法说「还剩几天」。列表里仍照旧显示「过期时间未知」 |
| J9 | 启动补查：应用启动时若已过当天 08:00 且今天还没发过，就补发一次。执行顺序排在通知权限请求之后 | 后台被系统掐掉时，这是最后一道保险。先拿到权限再发，否则第一次补查会被系统静默丢弃。代价是用户可能正在用应用时看到通知，可接受 |
| J10 | 通知小图标：图形就是项目已有的 `drawable/ic_cookie.xml`（Material Symbols cookie，用户已提供），按「用途命名」规范另存一份 `ic_notification.xml` | 品牌图形就是这枚饼干。同一 path 存两个文件是因为两个用途今后会分开变（界面上的图标跟主题色走，通知小图标只能单色剪影），合用一个名字会让「改通知图标」与「改界面图标」互相牵连 |
| J11 | 通知权限（`POST_NOTIFICATIONS`，API 33+）在 onboarding 结束、首次进主页时请求一次；拒绝后不反复弹，也不做应用内开关 | 与 N2 一致：不加设置页。系统设置里本来就能改 |
| J12 | 检查过程用进程内 `Mutex` 串行化 | 闹钟与 WorkManager 可能几乎同时醒，两条通道各发一次就破了 A1。同进程内一把锁够用（本项目没有跨进程组件） |
| J13 | `ExpiryReminderChecker` 不直接持有 `NotificationManager`，而是接受一个「把 `ReminderPlan` 发出去」的函数 | 幂等、分类、状态清理全靠单元测试盯住（见「测试」），而 `NotificationManager` 在 JVM 测试里不存在 |
| J14 | 闹钟的排期在**每次进程启动时**都重跑一遍（`FreshNowApp.onCreate`，幂等覆盖同一个 `PendingIntent`），不只在首次安装或设置变更时排 | 国产 ROM 里有一部分把「从最近任务划掉」当成强制停止，会把已注册的闹钟与作业一井吊销（见「风险」）。不重排的话，用户划一次卡就永久不再收到提醒，而他自己也不会知道 |
| J15 | 首页不新增任何提示条。通知权限被拒或后台被限制时，应用什么都不说 | 用户已在需求里定下「设置项先不做」；一条永远消不掉的提醒条就是变相设置页。代价是用户只会觉得「没提醒」，不会知道是权限问题 |

## 用户看到的样子

锁屏或通知栏，早上 8 点：

```
┌────────────────────────────────────┐
│ [F] FreshNow · 刚刚                 │  ← 小图标着色为 Warning40
│ 3 件即将过期                        │
│ 油麦菜 · 还剩 2 天                  │
│ 酸奶 · 还剩 1 天                    │
│ 菠菜 · 今天到期                     │
│                          查看        │
└────────────────────────────────────┘
┌────────────────────────────────────┐
│ [F] FreshNow · 刚刚                 │  ← 小图标着色为 Error40
│ 1 件已过期                          │
│ 牛奶 · 已过期 1 天                  │
│                          查看        │
└────────────────────────────────────┘
```

- 某一类没有内容时，那一条不发（只有过期的就只发下面那条）。
- 两条都为空时，什么都不发，也不占通知栏。
- 点任意一条 → 首页。
- 用户侧滑划掉，不影响当天下一次也不再发（当天已发过）。

## 技术设计

### 1. 分类（纯函数，可测）

新文件 `data/reminder/ExpiryReminderContent.kt`：

```kotlin
data class ReminderEntry(val name: String, val days: Long, val date: String)

data class ReminderPlan(
    val dueSoon: List<ReminderEntry>,   // 0..3 天
    val expired: List<ReminderEntry>,   // < 0 天，且未提醒过
)
```

- 输入：全部记录 + `today` + 已提醒集合。
- 过滤：`deletedAt == 0`；`ExpiryCalculator.daysRemaining(...)` 为 null 的跳过（J8）。
- 排序：`dueSoon` 按天数升序（最急在前）；`expired` 按过期天数降序（过期最久在前）？——不，过期最久的最该丢，但用户更关心刚过期的。**按过期天数升序**（刚过期的在前），与「还剩」那条的「最急在前」保持同一种读法。
- 名称重复时不去重（两盒牛奶就是两盒），除非同 `syncId`。

### 2. 「已提醒」状态

`data/reminder/ExpiryReminderState.kt`，沿用项目已有的 DataStore 写法：

- `lastNotifiedDate: String?`（`yyyy-MM-dd`，A1 的第一道保险）
- `notifiedExpiredKeys: Set<String>`，元素为 `"$syncId#$resolvedExpiryDate"`
- 每次检查成功后：写入 `lastNotifiedDate`，把本次发出的过期项的 key 并进集合，并**丢弃不再对应当前库中任何过期记录的 key**（集合不会无限长）。

### 3. 排期

`data/reminder/ExpiryReminderScheduler.kt`：

- `nextTrigger(after: ZonedDateTime): Instant` —— 下一个 08:00（今天还没到就是今天，已过就是明天）。纯函数，单独测。
- 用 `AlarmManager.setWindow(RTC_WAKEUP, triggerAt, 1h)`：非精确、无需权限、可被系统与其它唤醒合并。**不用 `setExact*`**（N3）。
- 闹钟由 `ExpiryReminderReceiver` 接收：先重排明天的，再执行检查。开机（`BOOT_COMPLETED`）、时区/时间变更（`TIMEZONE_CHANGED`、`TIME_SET`）也重排。
- WorkManager 兜底：`PeriodicWorkRequestBuilder<ExpiryReminderWorker>(24h)`，`initialDelay` 到下一个 08:00，`ExistingPeriodicWorkPolicy.UPDATE`。它在应用进程被杀、甚至重启后仍会被系统恢复。

### 4. 检查动作

`ExpiryReminderChecker`（被 receiver、worker、启动补查共用），整体在 J12 的锁里：

1. 若 `lastNotifiedDate == today` → 直接返回（A1）。
2. 读全部记录 → 算出 `ReminderPlan`。
3. 有非空列表就发对应通知；两类都空则什么都不发。
4. 写状态。

**注意**：`lastNotifiedDate` 只在「至少发出一条」时写。两类都空的那天不写，这样用户当天新扫了一盒酸奶、再打开应用时补查还能补发一条——否则「早上 8 点库是空的」会把一整天都锁死。

反过来，当天已经发过之后，用户再把某条记录的过期日期改成过去（当天新出现一个「已过期」），当天不会再补发一条「已过期」。这是 `lastNotifiedDate` 换来的确定性，刻意为之：同一天同一类提醒只有一条。

### 5. 通知

`notification/ExpiryNotifier.kt`：

- 两个渠道在 `FreshNowApp.onCreate`（新文件，`Application`）里创建，幂等。
- 标题 / 正文 / 行格式全部走 `strings.xml`：

| 新增串 | 内容 |
|---|---|
| `reminder_soon_title` | `%1$d 件即将过期` |
| `reminder_expired_title` | `%1$d 件已过期` |
| `reminder_entry` | `%1$s · %2$s`（名称 · 状态） |
| `reminder_more` | `另有 %1$d 件` |
| `reminder_channel_soon` | `即将过期` |
| `reminder_channel_expired` | `已过期` |
| `reminder_channel_description` | `每天提醒一次：有哪些东西快到期了、哪些已经过期` |

状态那半句复用 `home_expiry_days_left` / `home_expiry_today` / `home_expiry_expired`。

- `BigTextStyle`，`setColor(Warning40.toArgb())` / `setColor(Error40.toArgb())`，`setContentIntent` → `MainActivity`（`FLAG_IMMUTABLE`），`setAutoCancel(true)`。
- 小图标 `ic_notification`。

### 6. 权限与入口

- Manifest 加 `POST_NOTIFICATIONS`、`RECEIVE_BOOT_COMPLETED`，注册两个 receiver（`BOOT_COMPLETED`、`TIME_SET`/`TIMEZONE_CHANGED` 用 `RECEIVER_NOT_EXPORTED` 或静态注册的受限形式——按 API 37 的广播接收限制落地）。
- 运行时请求放在 onboarding 收尾处（与现有 onboarding 流程同一处，不新开页面）。

## 测试

- **分类**（JVM）：剩 4 天不提醒、剩 3 天进「即将过期」、今天到期进「即将过期」且措辞为「今天到期」、过期 1 天进「已过期」、墓碑记录不参与、推算失败的记录不参与、已提醒过的过期项不再出现、过期日期被改晚后重新出现。
- **排期**（JVM）：07:59 时下次是今天 08:00；08:00 整与 08:01 时下次是明天 08:00；跨月、跨年正确。
- **幂等**：同一天连调两次检查器，第二次不发（断言 notifier 的调用次数）。
- **状态清理**：记录被删后，对应的 `syncId#日期` 从集合里消失。
- **instrumented**（可选）：渠道创建、通知内容与点击 intent 指向 `MainActivity`。

## 风险

- **国产 ROM 上不保证送达**（已与用户确认）。纵深：AlarmManager + WorkManager + 开机重排 + 启动补查+启动重排，四条通道都在等一个「8 点之后打开应用」的兜底。仍会漏的场景：用户点了「强制停止」、长期不打开应用且未加白名单。**验收时要在真机上按机型实际验证**，不能只测模拟器。
- **「从最近任务划掉」在部分国产 ROM 上就是强制停止**。原生 Android（含 Pixel、模拟器）不是这样：划掉只是结束界面，已注册的闹钟与作业到点仍会执行（WorkManager 团队的 `pfmaggi` 在 googlecodelabs/android-workmanager#179 里的原话）。但部分中国 OEM 把划卡实现成了 force-stop，这是 CDD 违规行为且 Google 已知（android-workmanager#87 转述的官方回复：「some Chinese OEMs treat swipe to dismiss from Recents as a force stop... WorkManager will reschedule all pending jobs, next time the app starts up」，另见 issuetracker.google.com/issues/113676489）。小米的进程管理文档把「上滑清理」（`SwipeUpClean`）直接归为「用户主动触发」的杀进程入口；OPPO 机型上也有划卡后 `JobScheduler` 作业消失的报告（SO 50369116）。**这意味着：用户习惯性划掉后台卡片，第二天的提醒就不会来，直到他再打开一次应用。这条技术上绕不过去**（前台服务常驻是唯一的硬办法，但破了 A4），只能靠 J14 的启动重排把它变成「漏一次，下次打开就恢复」，并在真实机型上验收。
- **Android 原生的「应用休眠」是本功能最大的隐性威胁，且与国产 ROM 无关**。目标 API 30+ 的应用若「用户几个月未与之互动」，系统会把它置为休眠，效果**等同于强制停止**：不能跑作业或闹钟、收不到推送、运行时权限被重置，而且**休眠前已排的作业与闹钟都要重排**（developer.android.com/topic/performance/app-hibernation）。它不受「忽略电池优化」豁免，豁免开关是系统设置里的「暂停未使用的应用活动」。偏偏这类应用天然低频：用户完全可能一两个月不打开，一旦睡着，提醒不再发出，而没有提醒也就没人打开它——是个死循环。目前只能靠“收到提醒→打开应用”把这个循环维持下去。
- **force-stop 是单向的，白名单救不了它**。被强停的应用进入包管理器的 stopped state：收不到任何广播（包括 `BOOT_COMPLETED`，系统广播默认带 `FLAG_EXCLUDE_STOPPED_PACKAGES`），**重启手机也救不回来**，唯一的解除方式是用户直接启动一次应用（Android 15 行为变更文档「Changes to package stopped state」、阿里云移动研发文档）。因此自启动白名单能救的是「被杀进程 / 被限制后台」，救不了「已经被强停」；本功能在国产 ROM 上的硬边界就在这里。唯一的复活点是用户那次手动打开，所以 J14（每次启动重排 + 补查）不是优化，而是这个边界上唯一的着陆点。
- **用户侧设置是决定性的**（见上）。以小米为例，能用的一组是：自启动开、省电策略「无限制」、取消「未使用时暂停应用」、**最近任务卡片锁定**（后者才是防划卡强停的那一个，自启动管不了）。小米的 Powerkeeper 说明也印证了「无限制」即取消系统侧限制（dev.mi.com/xiaomihyperos pId=1628），但**仍有「自启动与电池优化都开了、两三天后 Worker 不再执行」的实测报告**（SO 78860338）。所以这组设置把成功率拉到「大多数时候能」，不是「一定」。
- **可检测「上次是不是被强停」**：API 35 起 `ApplicationStartInfo.wasForceStopped()` 直接给出这个信号。已经在 J14 的启动补查里顺带覆盖，不需要单独分支。
- **多设备重复提醒**：`notifiedExpiredKeys` 是本机的（J3），两台都装着应用、又都同步了同一条记录时，两边各提醒一次。这是刻意的取舍——把提醒状态塞进同步会让两台设备互相覆盖，漏发比重复更糟。
- **渠道重要性发布后不可调**（J4）。若上线后发现太吵，只能新建第二个渠道并迁移。
- **小图标**（J10）在 24dp 下可能太平，看不出是块饼干。真机验证时优先看这一项。
- 8:00 是设备本地时间；用户跨时区飞行后，重排依赖 `TIMEZONE_CHANGED` 广播，该广播在部分 ROM 上会被吞，最坏情况是当次偏移几小时。
