# 一条记录多张照片，与扫描页翻面收尾

日期：2026-10-16　状态：待批

## 为什么

两件事，一件是新的，一件是早就别扭的：

1. **一条记录只能配一张照片**——扫描保存那一刻抓的那一帧。用户要在一条记录上留几张：包装的正面背面、小票、同款买的几包。这些照片**只给人看**，AI 一个都不看：识别走的是实时扫描，每帧送模型，与存下来的照片无关。
2. **扫描过程中不能改任何东西**，而且收尾这一步现在是散的：保存后要填「位置」得进「补充信息」页，要改照片或名称又得从主页点进「编辑记录」页——**两页在管同一件事**。用户要的是：扫描只管扫，扫完再编，但步数不能比现在多。

## 目标

- G1 一条记录能配多张照片，最多 9 张；能加、能删、能看大图。
- G2 扫描页分两态：**扫描态**只有相机与只读结果；点「下一步」**同一个页面**翻成**编辑态**，相机收成一条可展开的边，露出照片九宫格与全部字段（名称、位置、生产日期、保质期、过期日期）。
- G3 页数不增反减：现有「补充信息」页与设置项「保存后接着填」一并退休。
- G4 局域网同步自然带上多张照片，用户无需任何操作。

## 非目标

- N1 照片不参与识别：不动 `AiVisionClient`、不动扫描的实时帧流与 `mergeObservation` 的字段规则（除了"手改锁定"，见下）。
- N2 不做照片排序、换封面、已有照片的再裁剪。新加的图沿用现有裁方与压缩路径。
- N3 不做批量导入（从相册一次选多张、各建一条记录）。
- N5 手动录入（主页那个入口）仍直接进编辑页，不经扫描页——它本来就没有可扫的东西。
- N4 不重做看图组件：沿用 `PhotoViewer` 与共享元素过渡。

## 反目标

- A1 **用户手写的字被后续识别帧冲掉**——一次都不能出现。
- A2 扫描态里出现任何输入框或照片格。
- A3 同一份表单出现两份实现（扫描页编辑态与编辑记录页必须是同一套）。
- A4 记录里出现指向不存在图片的名字，或磁盘上留下没人引用的照片。

## 约束

- 设计语言 Material Design 3，取值只从 `ui/theme/`（`FreshNowSpacing` / `FreshNowSize` / `FreshNowShapes`）取；组件规范见 material-3 技能。
- 记录的一切写入必须经 `ScanRecordRepository`（它负责盖 `updatedAt` / `updatedBy`，漏一处那次修改就永远同步不出去）。
- 图片文件名保持**内容散列**（`ScanImageStore`），不引入第二套命名；引用计数靠"名字集合"推导，不新增计数字段。
- 迁移必须有真实表结构与实体核对的测试（先例见 `MIGRATION_4_5` 的注释与 `ScanRecordMigrationTest`）。
- 界面变了 → baseline profile 需在虚拟机上重录。

## 我定的（实施时可推翻，但要说明理由）

| 编号 | 决定 | 理由 |
|---|---|---|
| J1 | 详情页：第一张铺满宽度（与现在一样），其下若还有别的图，给一排可点的缩略图；点大图或缩略图进全屏 | 与现有详情页差别最小；看图仍走 `PhotoViewer` |
| J2 | 主页列表的缩略图取第一张 | 列表只要一个代表，第一张就是用户最先给的那张 |
| J3 | 存储用 `imageNames: List<String>`（Room TypeConverter，换行分隔），**不建子表** | 同步的冲突判据（LWW）是"一行一个版本"；子表会把一行拆成多版本，墓碑、合并、破平全要重想。文件名是 hex + `.jpg`，不含换行 |
| J4 | 同步：`SyncRecordDto.imageName` → `imageNames`，拉图改为逐张按**内容名**取 | 内容寻址白送"对端已有就不必拉"这个判断 |
| J5 | 扫描页编辑态直接复用 `RecordEditForm`（该组件本来就与页面无关，可观测量在 `RecordEditFormTest`） | 避免 A3 |
| J6 | 「取消」（编辑态）＝ 折回扫描态，不是退出页面 | 与 D3/D6 一起构成"可来回"的闭环 |
| J7 | 未被引用的照片**不在删除那一刻删文件**，仍交给 `reconcileImages` 按引用集合收 | 同一张图可能被多条记录引用（内容寻址），当场删会删掉别人还在用的图 |
| J8 | 满 9 张时九宫格填满，「+」那一格消失 | 上限要看得见，否则点下去没反应 |
| J9 | 详情页：点缩略图 = 把主图换成它；点主图 = 进全屏（全屏内左右滑翻页） | 缩略图回答「看哪张」，全屏回答「看多大」，两件事各给一个手势 |
| J10 | 同步载荷**同时保留** `imageName`（取第一张）并新增 `imageNames` | 反向兼容：旧版本设备收到的载荷若缺 `imageName` 键，会**整条记录解不出来**（那边这个字段没有默认值）。新发给旧时旧版本只看到第一张，可接受 |
| J11 | 扫描态**不显示「已手改」标记**：扫描态展示的本来就是「这条记录当下的值」，与它来自识别还是手写无关 | 少一个标记少一处噪音；「交还给识别」的入口放在编辑态（那里有地方摆） |
| J12 | 编辑态点「+」仍走既有两条路：拍照页 `PhotoCaptureScreen` / 系统相册选择器 | 不新造取图方式 |
| J13 | 编辑页与扫描页编辑态允许滚动（两页本来就带 `verticalScroll` 与 `ScrollEdgeFade`），九宫格占三行不改变这一点 | 现成能力，不必为此重排版式 |

## 用户看到的样子

```
扫描态                          编辑态（同一个页面）
┌──────────────┐   下一步    ┌──────────────┐
│  相机画面     │  ───────→  │ 照片九宫格     │
│  ● 已读到 3 项│            │ 名称/位置/日期  │
├──────────────┤  ←───────  ├──────────────┤
│ 名称（只读）   │  继续扫描   │ ⌃ 继续扫描     │
│ 生产日期（只读）│            │ 取消      保存 │
└──────────────┘            └──────────────┘
```

- 编辑态里相机不是被销毁，只是收成底部一条「继续扫描」；展开即回扫描态，**已填的字与已加的照片都还在**。
- 编辑态不再往模型送帧；折回扫描态后接着送，但被手改过的项不再被覆盖（D6）。
- 折回后再翻面，表单显示的是那份草稿，不是重新识别出来的值。

## 技术设计

### 1. 数据

`ScanRecord.imageName: String` → `imageNames: List<String>`（有序，第一张即代表图）。

- Room `TypeConverter`：换行分隔的 TEXT（名字里不会有换行）。
- 空列表 = 这条记录没有图片（对应现在的空串）。
- DAO：`findAllImageNames()` 改成所有记录名字的并集（`flatMap`）；`updateImageName(syncId, name)` 改成**追加一个名字**（去重、幂等、**不碰 `updatedAt`**）。

### 2. 迁移 v5 → v6

`imageNames` 的旧值就是原来那一根 `imageName`。因为要同时改名与改类型，**重建表**（照 `MIGRATION_3_4` 的做法），把老值搬成单元素列表或空列表。

表结构必须与实体完全一致，由迁移测试拿实体核对（`ScanRecordMigrationTest` 里照 `migrate4To5_...` 加一条 v5→v6）。

### 3. 照片的增删

`ImageChange`（Keep / Remove / Replace）升级为多图语义：

- 每张现有图：保留、移除、替换。
- 追加若干新图（每张都是已编码的正方形 JPEG 字节）。
- 编辑态的删除**只动草稿**（J7），点保存时按最终名字列表落库，被丢下的文件由 `reconcileImages` 收走。
- 新加的图在草稿里只存字节，点保存才落盘（沿用编辑页现有约定：取消编辑不在磁盘上留下没人引用的图）。

### 4. 同步

- DTO 加 `imageNames: List<String>`；旧版本发来的载荷没有这个键 → 必须带默认值空列表（先例：`location` 的注释），否则老设备发来的记录整条都解不出来。
- 拉图：`/image` 现在按 `syncId` 取那一张，改为按**名字**取（`/image?name=`）。收到后写盘（内容寻址，写出来的名字必然等于对端给的名字），再追加进本地记录的名字列表（不盖 `updatedAt`）。
- 「缺图」判据：`imageNames` 里有名字但本地查不到文件 → 逐个补。
- 删除的墓碑语义不变：行删了图才可能被 `reconcileImages` 收走，因此墓碑期内误删有得救（与现状一致）。

### 5. 界面

- **扫描页**：`stage`（扫描态 / 编辑态）放进 `ScanViewModel`（要跨进程重建存活）；编辑态复用 `RecordEditForm`。
- **照片九宫格**：新组件 `PhotoGrid`（`ui/component/`），编辑页与扫描页编辑态共用。3 列，末尾「+」，每格右上角 ✕；点格子开大图。
- **编辑页**：照片栏由"一行缩略图 + 更换照片"换成 `PhotoGrid`。
- **详情页**：第一张铺满宽度（`ScanPhoto` 不变），多张时下方一排缩略图，全屏看图左右滑。
- **删除**：路由里的「补充信息」页、设置里的「保存后接着填」开关、以及 `BehaviorSettings.supplementAfterSave` 一并退休。

### 6. 扫描页两态与"谁说了算"

- 编辑态**不往模型送帧**（相机活着但不分析）。
- 手改过的字段进一个"已锁定"集合；`mergeObservation` 只写未锁定的字段。锁定状态应当可见（"这一格是你写的"），并且可以交还给识别。
- 落库之前一切都在内存：`ScanViewModel` 的草稿既服务扫描态的结果展示，也服务编辑态的表单，两份必须是同一份状态，否则折回一次就会分叉。

## 测试

- 迁移：v5→v6 把老的一张图搬成列表第一张；表结构与实体一致。
- DAO / Repository：多图写入、追加名字不盖 `updatedAt`、缺图判据、`reconcileImages` 按引用集合删孤儿（**同一张图被两条记录引用时不得删**）。
- 同步：多图 DTO 往返（含旧载荷缺键）、按名字补图。
- 界面：九宫格（含 9 张上限）、详情页多图与全屏翻页、扫描页两态切换与"手改不被覆盖"。

## 风险

- 九宫格在编辑页占的纵向空间比现在那一行多两行（9 张时），需确认表单不被挤到折叠线以下——这是当初把大图改小的原因。
- 编辑态同时挂 9 张位图的内存（每张 768² 约 2.4 MB），只在编辑态解码缩略图可以压住。
- 迁移重建表期间照片引用不变（只搬名字），但要求迁移测试覆盖"老记录无图"与"老记录有图"两条。
